# Incident Report — RunPod L4 ingest blocked on the Surya backend

**Date:** 2026-10-10  
**Pod:** `1w81f5nxcr7isc` (`healthcare-platform`)  
**Window:** about 16:49–17:46 IST  
**Status:** Open. Login and the three app processes are up. OCR of a 24-page PDF has not completed.

---

## Summary

`terraform apply` rented an NVIDIA L4 on RunPod Secure Cloud. Neo4j, Qdrant, Ollama (`medgemma:4b`), the reasoning API, the ingestion API, and the Blueprint UI all started. Login returned 200 after `.env.local` was filled in.

Ingest of `PMC13559776` failed in one second at the first OCR call. `data_ingestion.ocr.inference_backend: auto` saw the GPU and selected Surya's vLLM backend, which starts by looking for a `docker` binary. Secure Cloud pods do not have Docker.

The fallback, `inference_backend: llama.cpp`, is set on the pod copy of `config/app.yaml`. The prebuilt `llama-server` from llama.cpp `b11429` does not run on this image (glibc 2.35). A from-source CUDA build of that same tag was configuring and compiling when this note was written. It had not been installed over `/usr/local/bin/llama-server`, and the PDF had not been retried.

## Findings

### 1. Terraform does not print an SSH command

`infra/runpod/outputs.tf` emits `pod_id`, `public_ip`, `cost_per_hr`, and `blueprint_url` only. This apply left `public_ip` empty. Port `22/tcp` is requested on the pod, but the mapped public host and port are not outputs. The working command came from RunPod → Connect.

### 2. A fresh pod has no login password

`scripts/pre_requisites.sh` copies `.env.local.example` to `.env.local` when the file is missing. The example sets `AUTH_USERNAME=admin` and leaves `AUTH_PASSWORD_HASH` and `AUTH_JWT_SECRET` blank. The reasoning server treats a blank hash as unconfigured and returns 503 with `AUTH_USERNAME or AUTH_PASSWORD_HASH not configured`. The file is gitignored, so it is never on a new pod until someone runs `make auth-setup` and restarts `make dev`. Uvicorn reads `.env.local` only at process start.

The filename is `.env.local`. `env.local` without the leading dot is a different path.

### 3. `device: mps` does not run OCR on this GPU

The committed `config/app.yaml` still has `data_ingestion.ocr.device: mps`. There is no Apple GPU on the pod. `device` is only the Torch device for leftover detection weights. Recognition uses `inference_backend`. Setting `device: cuda` on the pod was the right Torch change. It did not select a recognition runtime.

### 4. `inference_backend: auto` requires Docker on any NVIDIA host

Surya v2 (`surya-ocr==0.20.0`) does not run recognition inside the Python process. `auto` picks vLLM when an NVIDIA GPU is present, otherwise llama.cpp. Warm-up only constructs `SuryaInferenceManager`. The log line `Surya v2 ready` means that object exists. The server is spawned on the first `predictor(images)` call.

That call entered `surya/inference/backends/vllm.py` and raised:

```text
surya.inference.backends.spawn.SpawnError: docker binary not found.
Install Docker and ensure the daemon is running.
```

[Production Startup](../guides/prod-startup.md) already says Docker is not available on RunPod Secure Cloud, which is why `make up` uses native Qdrant and Neo4j binaries. The OCR path does not have an equivalent fallback. Installing Docker inside this pod is not the supported layout.

The three-minute gap before `Rendering PDF pages…` was not the failure. Failure was immediate once `Running OCR on 24 page(s)…` was logged.

### 5. The published llama.cpp binary does not run on Ubuntu 22.04

After the pod config was set to `inference_backend: llama.cpp`, `llama-server` was absent. The llama.cpp `v0.6.0` nightly tag was `b11429`. These two archives were downloaded:

- `llama-b11429-bin-ubuntu-cuda-12.8-x64.tar.gz` (163 MB)
- `cudart-llama-b11429-bin-ubuntu-cuda-12.8-x64.tar.gz` (566 MB)

`/usr/local/bin/llama-server` resolved, then the dynamic linker rejected the build:

```text
llama-server: /lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.38' not found
llama-server: /lib/x86_64-linux-gnu/libstdc++.so.6: version `GLIBCXX_3.4.32' not found
```

Those symbols come from Ubuntu 24.04. This pod's glibc is 2.35. Do not upgrade the system glibc to satisfy the prebuilt binary.

Surya spawns `llama-server` with `-m`, `--mmproj`, `-ngl`, `--ctx-size`, `--parallel`, `--alias`, and `--jinja`, then downloads the Surya GGUF and mmproj from Hugging Face on first use. A binary that cannot start never reaches that download.

### 6. The source build was the open action

`nvcc` is `/usr/local/cuda/bin/nvcc` (toolkit 12.4.131). Driver 13.2 can run a CUDA 12.4 build. The L4 architecture is `sm_89`.

Configure of `/tmp/llama.cpp` (tag `b11429`, version string `0.6.0-dev`) completed with the CUDA backend included. `cmake --build build -j 8 -t llama-server` was still compiling CUDA objects when this report was written. The symlink at `/usr/local/bin/llama-server` still pointed at the glibc-2.38 binary under `/opt/llama/llama-b11429/`.

The replacement, once the compile finishes, is:

```bash
ln -sfn /tmp/llama.cpp/build/bin/llama-server /usr/local/bin/llama-server
llama-server --version
```

`--version` has to print a version and must not mention `GLIBC_2.38`. Then, from the repo root, `make dev-kill` and `make dev`. The warm-up line must say `inference_backend=llama.cpp`. Uvicorn does not watch `config/app.yaml`, and the running process caches the backend chosen at startup.

## Operator notes

- `make validate` staying green does not mean OCR can run.
- `Surya v2 ready` does not mean vLLM or `llama-server` has started.
- `make dev-kill` only exists in the repo root. From `config/` it reports `No rule to make target 'dev-kill'`.
- Ctrl+C of `make dev` printed `Segmentation fault (core dumped)` and `Terminated`. The services did stop. Use `make dev-kill` before starting again so ports 8000, 8002, and 5173 are free.
- Ollama and a future CUDA `llama-server` share the same 22 GB L4. `medgemma:4b` was pulled but not necessarily resident during the failed OCR call.
